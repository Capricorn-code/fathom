# ADR-009: アーキテクチャ方針 — 関数型パイプライン+依存方向ルール

## 状況

PR #22 のレビューで「DDD・クリーンアーキテクチャを最低限意識した構成にしたい」という要望が挙がった。fathomは現状、状態変更・永続化・複雑な不変条件を持たない「ファイル→変換→出力」の一方向CLIであり、どこまで形式的なアーキテクチャを採るかの判断が必要だった。

## 決定

**「関数型パイプライン+依存方向ルール」を正式方針とする。**

- パッケージ間の依存は一方向のみ: `cli → core`、`cli → masking`(M2〜)。coreの外部依存はzodのみに保つ。maskingは何にも依存しない
- core内も一方向のみ: `digest(層3)→ normalize(層2)→ raw(層1)`。逆方向のimportは禁止
- I/Oは端(層1のストリーム読み込み・cliの入出力)に隔離し、層2/3は純関数にする
- DDDは本質のみ採用: ユビキタス言語(docs/specの用語=型名)、ドメインの純粋性、境界の明示(「LLMに送れるのはSessionDigestだけ」を型と構造で強制)
- インフラ層の正式導入(ports & adapters化)は**Web版着手時に再評価**する。DB・認証・Stripe・LLM API等「差し替えたい外部技術」が現れた時点で層として切る
- 強制手段: パッケージ間はpnpmのnode_modules分離(未宣言依存はimport不可)。層間は規律+レビュー(機械化はファイル数が増えたら検討)

## 却下した代替案

- **戦術的DDDフル採用(Entity/Aggregate/Repository等):** 状態も永続化もない一方向パイプラインでは形骸化し、YAGNI違反
- **今すぐの完全クリーンアーキテクチャ(空のインフラ層を先に作る):** 差し替え対象が存在せず空箱になる。現行の規律で移行が「追加だけ」で済むことは担保済み
- **アーキテクチャ無方針(coreにI/Oや表示を混ぜる):** 将来のWeb版でのcore再利用(タスク②の設計意図)が崩れる
